# Web-app baseline, 13 Nov 2026 (kirana billing, 2 builds)

Method: real editor on wyberai.com, owned test account, Web app type, "Just build it" or default flow, current production command
(old system prompt, React 18 / Vite 5 / Tailwind 3 pins). Both builds were published and tested on their public pages
(`/app/kirana-khata-book`, `/app/kirana-billing-pro`), because clicks do not reach the sandboxed preview inside the editor.
Tested by Claude through the Browser pane; only what is marked "seen" was actually exercised.

## Build 1: plain prompt
"A billing app for my kirana store: add items with price and stock, make bills for customers, track udhaar (credit given) for each customer, and see today's sales."

- Time and cost: about 2 min 45 s; 30 credits (2107 to 2077); chip said about 30 to 34. Estimate matched the charge.
- Seen working: tap an item, qty stepper, bill number #1006, customer dropdown and add customer, Cash / UPI / Udhaar, save bill, toast,
  stock 24 to 23, daily totals that reconcile (cash 585 + UPI 285 + udhaar 204 = 1,074), 7-day chart, top items, export button.
- Persistence: seen. Reloaded the public page; stock stayed 23 (data is in the page's localStorage shim, so one browser only).
- Problems: starts with fake sample bills presented as real ("4 bills today, 920 in your galla" before any real sale), not labelled as demo;
  "Synced just now" label with nothing to sync; phone-width column with bottom tabs; page title "App | WyberAi" instead of a real title.
- Not tested: Items and Udhaar tabs, CSV export content, accessibility, keyboard, console errors, performance.

## Build 2: same prompt plus launch-ready requirements written into the prompt
(desktop and phone layouts; start empty with clearly labelled sample data; CSV import with preview; CSV export and print; owner/staff PIN roles;
change history; WhatsApp reminder for udhaar; keyboard and screen-reader friendly; Privacy and Data page with export and delete; say data is browser-only.)

- Time and cost: roughly 7 to 8 minutes (not timed exactly); 11 files; chip said 30 credits but 50 were charged (2077 to 2027).
  This reproduces the 10 Nov note (30 shown, 50 charged). Build 1 did not show it.
- Seen working: shop setup screen with inline validation in plain words ("Enter your shop name, it prints on bills"), honest copy
  ("data is saved in this browser only", "PIN cannot be recovered"), real page title, empty-start "Start in 3 steps", empty-state shelf with
  Add item / Import CSV / Load sample data (demo), Today at 0 rupees and 0 bills until real use, Privacy and Data entry in the nav.
- Not tested: CSV import actually parsing, export content, print, change history, WhatsApp link, PIN enforcement, delete-my-data,
  desktop sidebar layout (the test viewport was narrower than 1024 px), keyboard and screen-reader behaviour, console, performance.
- Honesty risk: an owner PIN stored in the browser is a screen lock, not security; the app says data is local but does not say the PIN
  can be bypassed.

## What this baseline changes in the plan
1. The current model follows a long, specific contract even under the old system prompt, so much of the spec is prompt work, not engineering.
2. Device persistence already works through the sandbox's localStorage shim (the model writes to localStorage). Sharing across devices does not exist.
3. Publish & Share already has a launch kit (share card, QR, WhatsApp, X, Facebook, Instagram). Item D8 of the spec is partly done.
4. The estimate-versus-charge mismatch is real and reproducible on larger builds.
5. Still missing in both: a verification report, shared or logged-in data, desktop layout evidence, accessibility checks.
